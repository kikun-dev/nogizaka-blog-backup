# SakaClip（サカクリップ）

SakaClip は、乃木坂46・櫻坂46・日向坂46の公式ブログを保存する**非公式の個人制作ツール**です。補足名称は「坂道ブログ保存ツール」です。各グループの公式サービスとは関係ありません。Web 画面でグループ、メンバー、保存内容、取得範囲を選べます。メンバー欄にはグループ全体の最新記事を選ぶ「全件」のほか、期別ブログ、運営スタッフ、ポカも含まれます。写真は最大20件のブログから取得し、画面での長押し保存とZIP保存ができます。通常のブログ保存は1ジョブ最大10件、投稿者別の全件バックアップは公式一覧の最後まで取得して PDF・MHTML・メタデータを1つのZIPにまとめます。

ブランド画像の原画は `assets/brand/SakaClip_icon_selected_original.png` です。アイコンと共有プレビュー画像は `npm run brand:build` で原画から再生成できます。原画のSC・クリップ・グラデーションを保持し、外側の白い余白だけを取り除いています。

共有画像の再生成には `assets/brand/fonts/` に同梱した IPA Gothic と DejaVu Sans Bold を使用します。各フォントのライセンス文書も同じディレクトリに置いています。

共有プレビュー画像の絶対URLにはVercelのシステム環境変数を使います。独自ドメインなどを明示したい場合のみ、Web環境に `SITE_URL`（例: `https://example.com`）を設定します。ワーカー側には不要です。

## 必要な環境

- Node.js 24.22.1（`.nvmrc` 指定。Vercel は `engines.node: 24.x` で24系を選び、パッチを自動適用）
- npm（Node.js 24 に付属する版）
- Playwright Chromium

## セットアップ

```bash
nvm install
nvm use
node --version
npm install
npx playwright install chromium
```

Node.jsをnvm以外で管理する場合も、公式のNode.js 24.22.1以降の24系LTSを使用してください。公開ワーカーを動かすWSLでも `node --version` が修正版を示すことを確認してから、依存関係を再インストールしてワーカーを再起動します。

`.env.example` を参考に `.env.local` を作成し、`LOCAL_ACCESS_TOKEN` に推測されにくいランダムな値を設定してください。例: `openssl rand -hex 32`。この値は Git に登録せず、ブラウザの「ローカルアクセストークン」欄に入力します。

## ローカル Web アプリ

```bash
npm run dev
```

PC のブラウザで `http://localhost:3000` を開きます。アクセストークンを入力するとメンバー一覧が自動で読み込まれます。グループ→メンバー→「写真のみ」または「ブログ」→取得範囲の順に指定します。メンバー欄の「全件」はグループ全体の公式一覧を更新順に表示し、投稿者を問わず「最新1件」「最新N件」「ブログを選ぶ」で少数件を保存します。写真は最大20件、ブログは最大10件です。メンバー欄で「全件」を選んだ場合、取得範囲の「全件バックアップ」は利用できません。個別の投稿者を選んだ場合は「全件バックアップ」も選べ、分割処理と保存先の注意事項が表示されます。ブログ選択画面ではページを移動しても選択が残ります。件数上限は画面とサーバーの両方で確認し、選んだブログは公式一覧とも照合します。

「写真のみ」では「最新1件」「最新N件」「ブログを選ぶ」で条件を確認し、「写真を取得」を押します。押すと写真の結果画面へ切り替わり、取得中の状態と完了後の写真を同じ画面で確認できます。「条件設定に戻る」で選択を保ったまま戻り、「写真の取得結果を見る」で再表示できます。取得後はブログごとに写真が縦に表示され、個別保存とZIP保存ができます。写真0枚のブログと、写真の一部を取得できなかったブログは、その場に状態を表示します。写真モードではPDF/MHTMLを生成しません。

「ブログ」で「最新1件」「最新N件」「ブログを選ぶ」を指定し、条件確認後に保存を開始します。結果画面には進行状況と ZIP の保存ボタンを表示します。ZIP 内は `Nogizaka/メンバー名/日付_ブログID_タイトル/blog.pdf`・`blog.mhtml`・`metadata.json` の構成です。グループ全体から複数投稿者の記事を保存した場合も、記事ごとの投稿者別フォルダに分けます。メタデータには投稿者 ID・名前・種別を含めます。ファイル名に使えない文字は安全な文字へ置き換えます。条件確認後は、対象ブログのタイトルと公式一覧に掲載された日時を表示します。選択一覧は公式サイトの一覧ページを読み、5分間だけサーバー内でキャッシュします。乃木坂46のグループ全体一覧では、投稿者の特定のため各記事の個別ページも確認します。ブログ本文を保存用に開くのは保存を開始したときです。公式一覧にないブログは個別ページの URL を直接入力できます（投稿者 ID は不明として保存します）。

全件バックアップは取得範囲の「全件バックアップ」を選び、注意事項と条件を確認して開始します。内部では最大10件ずつ取得し、通常は同じジョブで最後まで進んで1つのZIPを作ります。1ジョブの上限は5,000件・保存データ19 GB・ZIP20 GBです。上限に達した場合も保存済み分をZIPとして確定し、結果画面に次の一覧位置を表示します。「続きから全件バックアップを開始」でその位置から新しいジョブを作り、次のZIPを受け取れます。続きのジョブの画面から以前のパートのZIPも保存できます。画面を閉じてもジョブは続き、アクセストークンを再入力して「前回の全件バックアップの結果を見る・再開する」から進捗に戻れます。取得中の失敗やサーバー再起動では保存済みのブログを保持したまま同じジョブを再開でき、ZIP作成中の失敗はZIPだけを作り直します。作成中は保存データとZIPの両方を置く空き容量が必要です。4 GB以上のZIPはWindows標準の「すべて展開」でエラーになる場合があります。ダウンロード後は7-ZipなどZIP64対応アプリで展開してください。通常のブログ保存は出力とZIPがそれぞれ512 MBまでです。

通常の件数指定では処理済み件数、成功・失敗件数、処理中の記事タイトルと投稿日を表示します。記事単位で失敗しても残りを続け、成功分は ZIP または写真一覧で利用できます。「失敗した記事だけ再試行」では失敗記事だけを新しいジョブへ渡し、元の結果も画面から戻って確認できます。写真0枚の記事は正常な取得結果として扱い、一部の画像を取得できなかった記事と区別します。全件バックアップは記事の欠落を避けるため、従来どおり失敗時に中断して保存位置から再開します。

ジョブ状態は `.local-data/jobs/` に記録します。保存ファイルは `.local-data/archive/<jobId>/` に置きます。写真モードの画像と `photos.zip`、ブログモードの PDF・MHTML・`blogs.zip` もジョブ単位のフォルダに保存します。同じブログを再取得すると、`.local-data/archive/_blog-cache/` の保存済み PDF・MHTML を再利用します。これらは Git の管理対象外です。保存先を変えたい場合は `.env.local` へ `LOCAL_ARCHIVE_ROOT` を設定します。同時に実行する取得処理は1件、待機は最大10件です。サーバー再起動時に未完了だったジョブは、次の API アクセス時に失敗状態へ変更されます。

この保存先はアプリを実行するマシン上のフォルダです。別のサーバーへデプロイすると、そのサーバー上に保存されます。利用者の端末へはZIPのダウンロードで渡します。利用者が端末側のフォルダを選んでPDF・MHTMLを直接書き込む機能は、ブラウザのフォルダ選択APIへの対応が必要です。

スマホで画面を確認する場合は、開発 PC とスマホを同じネットワークに接続し、スマホから `http://<開発PCのLAN内IPアドレス>:3000` を開いて同じアクセストークンを入力します。PC のファイアウォールが接続を遮断する場合は、ローカルネットワークからポート 3000 へのアクセスを許可してください。

### iPhone・iPadで写真を保存する

1. iPhone・iPadと開発PCを同じWi-Fiに接続し、Safariで `http://<開発PCのLAN内IPアドレス>:3000` を開きます。
2. `.env.local` の `LOCAL_ACCESS_TOKEN` と同じ値を画面に入力します。
3. グループ、メンバー、「写真のみ」、「最新1件」を選んで「この条件を確認」→「写真を取得」を押します。
4. 「取得した写真」に表示された写真を長押しし、Safariのメニューから「写真に保存」を選びます。写真アプリで保存結果を確認します。

### Androidで写真を保存する

1. Android端末と開発PCを同じWi-Fiに接続し、Chromeで `http://<開発PCのLAN内IPアドレス>:3000` を開きます。
2. `.env.local` の `LOCAL_ACCESS_TOKEN` と同じ値を画面に入力します。
3. グループ、メンバー、「写真のみ」、「最新1件」を選んで「この条件を確認」→「写真を取得」を押します。
4. 「取得した写真」に表示された写真を長押しし、Chromeのメニューから「画像をダウンロード」を選びます。ダウンロード先で保存結果を確認します。

ZIPを使う場合は「写真をZIPで保存」を押します。iPhone・iPadではZIPは通常「ファイル」アプリに保存され、写真アプリへ直接入りません。写真アプリへ保存したい場合は、画面に表示された写真を個別に長押ししてください。

## 既存 CLI

Web 化の間も従来の CLI を使用できます。

```bash
npm run archive -- \
  --url 'https://www.nogizaka46.com/s/n46/diary/detail/ブログID' \
  --output '~/Documents/SakamichiBlogArchive' \
  --limit 1
```

開始 URL からグループを自動判定します。投稿主体別の一覧ではなく、ブログの個別 URL を指定してください。主なオプションは `--limit 3`、`--delay 5000`、`--headed`、`--force` です。期別ブログやポカなども投稿主体別のフォルダに保存します。既存の `index.json` にある `memberName` は読み込み時に `authorName` として扱い、次の保存時に新形式へ移します。

## 共通取得エンジン

CLI は `lib/archive/index.mjs` の `archiveArticles()` を呼びます。同じモジュールの `inspectArticle()` はブログのタイトル・投稿主体・投稿日などを保存前に取得でき、Web サーバーからは `server/archive-engine.ts` 経由で両関数を呼べます。ブログ情報の確認では画像の読込状態をその時点の値として返し、PDF/MHTML 保存では従来どおり画像の読み込みを再試行します。

`lib/archive/` は、グループと URL、ブログ取得・メタデータ・画像、PDF/MHTML 生成、投稿主体別の索引・ファイル保存をモジュールごとに分けています。

```bash
npm run lint

```

`test:ui` はローカルの Next.js と Playwright Chromium を起動し、公開 API の応答をテスト内で差し替えて画面状態を検証します。Supabase・R2 には接続しません。初回はセットアップ手順どおり Chromium をインストールしてください。

## 公開モード（Issue #9）

公開モードは Next.js Web/API、Supabase、Cloudflare R2、`npm run worker` の4要素で構成します。Web は Vercel、ワーカーは当面 WSL2 上で動かします。メンバー・記事一覧の取得も Supabase 経由でワーカーへ依頼するため、公開 Web API では Playwright を起動しません。ワーカーは Supabase へ外向きに接続するため、開発 PC のポート開放は不要です。OCI へ移す場合も同じワーカーと環境変数を使えます。

友人へ公開する際の使い方と注意事項は [友人向け利用案内](docs/friend-guide.md) にまとめています。アクセスコードは案内文とは別に本人へ渡してください。

1. `supabase/migrations/` の SQL をレビューし、Supabase CLI の `db push` で対象プロジェクトへ未適用分を適用します。リモートの SQL Editor で別途テーブルを作らないでください。`20261022120000_service_role_table_privileges.sql` は、Web とワーカーが直接使うテーブルの最小権限を `service_role` に付与します。
2. `.env.example` の公開モード用変数を、Vercel とワーカーのそれぞれに設定します。`SUPABASE_SECRET_KEY` と R2 のキーはブラウザ向け変数にしません。Vercel にはバケット限定の Object Read キーを別に作成して設定し、ワーカーには既存の Object Read & Write キーを設定します。
   Vercel のプロジェクト設定では Node.js 24.x を選びます。`package.json` の `engines.node` も24.xを指定しています。デプロイの Build Logs で Node.js の版を確認し、24系の最新セキュリティパッチが使われていることを確かめます。
3. WSL2 では `WORKER_OUTPUT_ROOT` に空き容量のある絶対パスを指定します。ワーカーは開始前に2 GB以上の空き容量を確認し、専用の `sakamichi-worker` サブディレクトリだけを一時領域として使用します。実行中は `npm run worker` を起動したままにします。Web を更新したらワーカーも同じコミットへ更新して再起動してください。古いワーカーは確認済み記事の固定処理に対応していません。
4. まず `APP_MODE=public` のローカル Web とワーカーで、最新1件の写真、少数記事のブログ、ZIPを確認します。成果物はジョブ完了から24時間後にアプリから利用不可になり、設定済みのR2削除ルールで後から削除されます。

公開版では全件バックアップと個別 URL 入力を無効にします。通常ジョブは1セッション1件、全体で実行1件・待機10件、写真20記事・ブログ10記事、出力は512 MBまでです。確認画面で表示した記事をジョブへ固定し、確認から15分以内に開始できます。期限が切れた場合は取得条件をもう一度確認してください。公開ワーカーはブログの永続キャッシュを作らず、古い公開ワーカーのキャッシュも起動時に削除します。ワーカーが停止している間はジョブが待機します。PCのスリープや再起動でリースが切れたジョブは失敗とし、画面から未取得の記事を再試行できます。セッションは通常ログインから24時間有効で、実行中のジョブがある間とその成果物の期限まで延長されます。アクセスコードの期限を越えてセッションが延長されることはありません。Cookie はその延長を利用できるよう7日間保持しますが、実際のアクセス可否はDB上のセッションとコードの状態で判定します。署名付きダウンロード URL の有効期間は5分です。コード失効後はアプリから新しいURLを発行しませんが、発行済みURLは最大5分間利用できる可能性があります。

### 友人別アクセスコードの運用

コード発行・一覧・失効は、`SUPABASE_SECRET_KEY` を持つ管理者環境でのみ実行します。

```sh
npm run access-codes -- create --name "表示名" [--expires-at "2026-12-31T00:00:00Z"]
npm run access-codes -- list
npm run access-codes -- revoke <UUID>
```

発行時に表示する平文コードは一度だけ安全な経路で本人に共有してください。DBにはSHA-256ハッシュのみが保存され、一覧出力にも平文・ハッシュは含みません。個別失効時は既存セッションを即時期限切れにし、待機中・実行中ジョブと一覧取得を失敗としてフェンスします。コード期限切れも認証とDBジョブ処理の双方で拒否します。

#### 旧 `SHARED_ACCESS_CODE` からの移行

この移行は全ログインを切り替える破壊的変更です。短いメンテナンス時間を確保し、次の順に実施してください。

1. 利用者へ停止時間を案内し、ワーカーを停止します。完了を待てない実行中ジョブはmigrationで失敗にし、リース世代を進めて旧ワーカーの完了を書き込めないようにします。すでにR2へアップロード中の未登録オブジェクトは残る可能性があり、設定済みR2ライフサイクルルールで削除します。ジョブ・セッション行は削除しないため、履歴と外部キー関係を保ちます。
2. 事前確認済みの `20261024100000_friend_access_codes.sql` を `supabase db push` で適用します。旧セッションを期限切れにし、migrationと新デプロイの間に旧アプリが作るコード未関連セッションもDBトリガーで即時期限切れにします。
3. 新アプリをVercelへデプロイします。切り替え中に旧アプリが旧コードへ成功応答を返す場合がありますが、DBがセッションを即時期限切れにするため保護対象へはアクセスできません。新アプリのデプロイ後は旧コードを認証しません。既存ログインも復元せず、新コード発行までログイン停止時間が続きます。
4. `npm run access-codes -- create --name "管理者"` と友人ごとの発行コマンドを実行し、平文を各利用者へ安全に共有します。管理CLIの管理者認証には `SUPABASE_SECRET_KEY` を使い、別の管理者ログインコードや管理画面は設けません。
5. Vercelとワーカーから `SHARED_ACCESS_CODE` を削除します。新バージョンのワーカーを起動し、複数コードでのログイン、所有者分離、ジョブ、写真、ZIPを確認してからメンテナンス終了を案内します。

ロールバックで旧環境変数を戻したり、既存セッションを再有効化したりしないでください。DB migrationは安全上ロールバックせず、問題時はメンテナンス状態を保って前方修正したアプリを再デプロイします。旧コードと既存セッションは復元されません。migration後に旧アプリへ戻した場合も、旧アプリが発行するセッションは期限切れとなりログインは失敗します。

Vercel Authentication を解除して友人に公開する前に、アプリ側のアクセスコードと所有者確認を検証します。解除後も、未ログインの API・成果物アクセス拒否と他利用者のジョブへのアクセス拒否を公開 URL で再確認します。Supabase Free は低利用が続くと休止する場合があります。その場合はプロジェクトを再開してからワーカーを起動します。
