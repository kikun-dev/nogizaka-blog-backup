# PR レビュー補助

PR 番号があれば PR 本文、関連 Issue、`main` との差分を読む。番号がなければ現在のブランチと `main` の差分を対象にする。Issue の完了条件に対する実装と検証の証拠を確認する。

## レビューしないこと

- Typecheck・Lint・Build の再実行や、コードスタイル・フォーマットの機械的な判定。PR に記載された検証結果と完了条件の対応は確認する。
- UI の視覚的な品質評価や、デザイン案との比較。
- 差分と無関係な既存コードへの改善要求。将来の注意点は「補足」に記す。

## レビュー観点

- **セキュリティ**: 入力・URL・保存先の検証、秘密情報の露出、外部コンテンツを扱う境界。
- **設計整合性**: Issue の意図と既存の構成・CLI 契約への適合、実行境界とエラー処理、既存パターンからの不要な逸脱。
- **パフォーマンス**: 不必要な通信・再試行・重複処理、大きなアーカイブの処理に伴う負荷。
- **将来拡張性**: 既知の API 置き換えや worker 差し替えを不必要に難しくする結合。

## 出力形式

日本語で次の見出しを必ず使い、該当する指摘がなければ「なし」と書く。

```markdown
セルフレビュー結果（観点: セキュリティ / 設計整合性 / パフォーマンス / 将来拡張性）

## P0
なし

## P1
なし

## P2
なし

## 補足
なし
```

## 分類基準と指摘の書き方

- **P0**: マージ前に必ず修正すべき重大問題。セキュリティ欠陥、データ破損、明確な重大バグなど。
- **P1**: マージ前の修正を強く推奨する問題。
- **P2**: 今回の PR で直すと望ましい改善点。
- **補足**: 問題ではない確認結果、残る検証上の制約、将来の注意点、未確認事項。
- 各指摘に対象の `ファイルパス:行` または関数名、問題点と理由、具体的な修正方針を書く。P0・P1 は優先度の理由も示す。
- 差分から確認できない点は推測で断定せず、「未確認」として補足に書く。設計レベルの別件は新しい Issue を提案する。

## 出力先

既定では会話にレビュー結果を提示する。PR への投稿を明示的に依頼された場合は PR コメントに投稿し、投稿内容の要約とコメントの URL も会話に示す。PR がない場合は会話に提示する。このスキルによるセルフレビューだけで必須のユーザーレビューを完了扱いにしない。
