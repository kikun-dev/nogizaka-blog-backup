# Issue 着手

1. Issue 本文・コメント・関連 Issue と、Issue が参照する資料を読み、完了条件と依存関係を整理する。前提 Issue が未完了なら着手可否を確認する。結果を左右する設計判断が未決定なら、選択肢・推奨・根拠を提示して決定を待ち、決定を Issue に記録する。判断が不要なら理由を示す。
2. 現状のコード、類似実装、差分を確認し、従うべき実装パターンを特定する。既存の未コミット変更は保護し、別 Issue の変更を混ぜない。
3. `origin/main` を確認し、`feature/<Issue番号>-<slug>`（修正は `fix/`、運用整備は `chore/`）の専用ブランチを作る。
4. 次の実装計画を会話で提示してから実装する。設計上の決定は Issue に残す。

## 成果物: 実装計画

移植元の「実装順序」「変更ファイル一覧」「検証計画」「PR 分割方針」「仮定・不確定要素」を、このリポジトリ向けに次のように明記する。

- **実装順序**: 依存関係に沿った変更の順番と、その理由。
- **変更ファイル一覧**: 変更が見込まれるファイルと、それぞれの変更内容。
- **検証計画**: Issue の完了条件ごとに、実行するテスト・コマンドと手動確認手順を対応付ける。`package.json` に存在する scripts を確認し、実行できない検証も明示する。
- **PR 分割方針**: 原則 1 Issue = 1 PR。差分が大きく別の責務を含む場合は、着手前に Issue と PR の分け方を提案する。
- **仮定・不確定要素**: 計画の前提、未決定事項、確認が必要な点。

## 完了条件

- 必要な設計判断が確定して Issue に記録されている。または判断が不要な理由が示されている。
- Issue 専用ブランチが作成されている。
- Issue の各完了条件に対応した実装計画が会話で提示されている。

このリポジトリの目標順序はローカル動作確認 → API の置き換え → 公開準備。後続 Issue の実装を先取りしない。GitHub 操作は `kikun-dev/nogizaka-blog-backup` を対象にする。
